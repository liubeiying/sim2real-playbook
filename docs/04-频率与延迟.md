# 控制频率与通信延迟

## 症状

- 真机发抖、动作不连贯
- 指令明明发了，动作慢半拍
- 仿真里平滑的轨迹，真机上一段一段的

## 根因：两条链路的频率差

```
下行指令流：推理节点 50 Hz → 安全限幅 → DDS → 底层总线 1000 Hz → 电机
上行状态流：编码器 / IMU 采样 → 时序对齐与滤波 → 构造观测 → 策略
```

50 Hz 与 1000 Hz 之间存在 20 倍频率差。策略每 20 ms 给一个目标位，底层每 1 ms 执行一次伺服——中间必须有插值和相位对齐，否则机器人会一顿一顿。

## 排查清单

- [ ] 策略推理频率实际是多少（实测，不要信配置）
- [ ] 底层总线周期是多少
- [ ] 中间是否做了插值
- [ ] 端到端延迟实测（发布时刻 → 电机响应时刻）
- [ ] DDS QoS 配置是否匹配

## DDS 一个特别阴的坑

ROS 2 里发布端与订阅端 QoS 不匹配时，**消息收不到且不抛异常**。

表现是：`topic list` 看得到话题，`echo` 就是没数据。我在这上面耗过时间，现在链路不通先查 QoS 再查代码。

```bash
ros2 topic info /your_topic --verbose
```

## 参考值与实测值

参考值是上游代码里写死的周期，可以用它当基线判断自己测出来的是不是正常；实测值那一列等我做完端到端测量再填。

| 指标 | 参考值 | 来源 | 我的实测 | 测量方式 |
|---|---|---|---|---|
| 策略控制周期 | 20 ms（50 Hz） | `unitree_rl_gym` C++ 部署控制器 | 待补 | 待补 |
| 底层总线周期 | 1 ms（1000 Hz）级伺服 | 常见人形底层总线规格 | 待补 | 待补 |
| 端到端延迟 | — | 无公开基线，必须自测 | 待补 | 发布时刻 → 电机响应时刻 |
| 关节跟随误差 | — | 无公开基线，必须自测 | 待补 | 目标角 vs 实际角差值 |

延迟不量化就没法优化。宁可先记一个粗糙的实测值，也不要空着——有了基线才知道改动是变好还是变差。
